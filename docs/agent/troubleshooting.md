# troubleshooting — 故障纪律

> 由 AGENTS.md §真相源 触发加载:测试红/bug/异常行为,处理前必读。

## 问题必记台账(2026-11-13 定,YPJ-172 会话)

凡遇到问题(测试红、bug、异常行为),无论大小,处理后必须记入 `docs/planning/问题处理记录.md`:症状、root cause(实锤才准写「根因」,未实锤标假设)、修复方法、预防,各一句;与 e2e 归因纪律衔接——实锤前只进「flake 桶」作记录。

## e2e 归因纪律(2026-11-08 升格,元因见 `docs/planning/2026-11-08-apihttp-0113-复盘.md`)

红例必须**读 trace + 查库实锤**后才许下结论——单跑绿不能当「漂移」证据(负载型问题单跑永远复现不了;A32/A46/F8 同款陷阱),error-context 的 DOM 快照可能是陈旧帧;**flake 桶只作记录不作结案**,条目带复现计数,同用例跨会话累计第 3 次红即强制 root-cause(project-settings 覆盖竞态在桶里躺了多届、YPJ-147 board-membership 同案,均为真 bug)。

**实操教训(全文见台账)**:

- 红例先留痕(测试结果目录/trace)再复跑——trace 会被重跑清掉,两次踩中(F8);AOP 访问日志(`docker logs`)是被重跑清不掉的旁证。
- 悬挂型超时先看 trace 有无测试体步骤:无 = API 预置悬挂,有 = 断言悬挂(A46)。
- 诊断先确认「哪个入口/环境/有无新产物」再归因;探针先确认端点口径再下结论(A47:详情接口与甘特接口的 actualStart 口径不同)。
- 反证探针:每个结论先明确「什么证据能推翻它」,证实与证伪都做(七规 #4,development.md §交付)。
- 归因必须实锤(查库/直调 API),未实锤只标假设,禁入「勿走回头路」与 handoff 结论。
- 「点击/操作无反应」第一步 = 从 handler 起逐行读完调用链到渲染,再谈环境;禁止先装工具/起服务/查容器(2026-11-24 定,YPJ-238 一行 bug 绕五轮环境,复盘见 planning/2026-11-24-ypj238-箭头排序-复盘.md)。
- 前端自验断言「用户可见结果」(界面顺序/文本/可见性),不是「请求 200/204」;「后端对+界面错」= 渲染 bug,直接读渲染代码。
