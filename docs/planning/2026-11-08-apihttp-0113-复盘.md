# 复盘:api.http 0113 节连续失败三轮(2026-11-08,YPJ-160 手验期)

> 三轮复发、前两轮归因皆错、第三轮才实锤。本文记录时间线、每轮的错误归因、真正根因、已落地的修复,以及防复发的硬规则(已同步进 AGENTS.md)。

## 症状(三轮同一表象)

IntelliJ 跑 `backend/script/api.http` 的 spec 0113 节:

```text
PATCH http://localhost:8082/api/projects/CHE*/groups/{{reparentGroupId}}
java.net.URISyntaxException: Illegal character in path at index 52
```

`{{reparentGroupId}}` 未被替换 → 建组请求(S-0113)捕获失败或未执行 → 后续正例+三个负例连环报错。**同一表象,三轮根因不同**——这是本轮复盘最大的教训。

## 时间线与归因纠错

### 第 1 轮(11-07 晚,项目 CHE244559)

- **现场**:DB 查实 CHE244559 在 yangzhou_test 已不存在;`reparentGroupId` 未定义。
- **真因(这轮对了)**:用户先在 test 跑了 api.http,随后整跑 e2e → **globalSetup 清掉 test 库**,手测数据连锅端;旧 IntelliJ 会话变量(pkey/token)指向尸位数据,setup POST 失败 → 变量不回填。
- **当时修复**:加 dev 环境(8081)建议切 dev 跑 → **后被用户拍板否决**(见硬规则 R1),此修复方向本身错误。
- **错误归因**:同晚 e2e group-types 红例被我按「单跑绿=漂移」结案 → **错**,当晚二次复现证明是真问题(见下)。

### 第 2 轮(11-08 凌晨 03:28)

- **现场**:用户「什么都没改重跑,还是错」。我第一反应查的是 e2e 现场(trace 挖出 POST 首击 4.5s 吃穿 5s expect 窗口),修了 `playwright.config.ts` expect 10s。
- **e2e 那半是对的**:trace 实锤 POST /groups wait=4461ms(JVM 首击),修复后全量 91 passed。
- **api.http 那半又错**:用户说「一样的错」实指 api.http,我却按 e2e 理解并回复。**没先问「你跑的是哪个」就开修**。

### 第 3 轮(11-08 03:44,项目 CHE512478)

- **决定性证据**:DB 还原现场——CHE512478 里**有** Epic 2/item/负例组,**没有** sprint2 类型、Epic 1、S-0113。静态 body(无变量)的请求不可能因变量失败 → **它们压根没被发送**。
- **真因**:**0113 节横跨 0110/0111/0112 三个上游节取变量**(`l1Key`、`parentGroupIdSample`、`itemId`)。任何一次执行没严格从头覆盖全部上游(点单节、跳跑、中途中断),0113 的建组就踩空或用上一轮过期值 → 捕获失败 → URISyntaxException。**人类执行必然踩空,是文件设计错,不是操作错。**
- **修复**:0113 节重写为**完全自含**(自带项目/类型/双 Epic/留守叶组/item,变量全带 `160` 后缀),curl 在 8082 逐请求复刻 18/18 全绿后交付。用户实跑通过。

## 顺手实锤的其他坑(防重蹈)

| 坑 | 事实 |
|---|---|
| 项目 key 长度 | `^[A-Z][A-Z0-9]{1,9}$` = 2–10 位;`CHE160+6位run`/`CP160+6位` 都超长,探针两次 FAIL 才钉到 `P160+6位`。**造 key 前先数长度** |
| `===` 分隔符 | HTTP client 只认 `###` 作注释/分隔;`===` 行被当非法请求(已在 288f1f8 修) |
| api.http 序号映射 | IntelliJ 报的 `api.http#71` 是「文件内请求序号」,与 grep METHOD 行数差 1(文件头有元请求),排查时先对表再下结论 |
| 幻影快照 | Playwright error-context 的 DOM 快照可能是失败窗口早期帧(弹窗刚打开时),「弹窗开着+字段空」不等于最终态;终态以 trace 最后 frame-snapshot 为准 |
| 设置面板覆盖竞态 | ProjectSettingsPanel 打开时异步拉当前设置;落地前用户的开关切换会被响应 `setMilestone(false)` 覆盖,PATCH 把旧值存回(e2e「重开恢复」惯犯红,DB 实锤 milestone_enabled=f)。修复=加载完成前禁用开关/保存;**同款 fetch-on-open 模式在 MilestoneManager 等面板也存在,属已知模式** |
| POST 首击尖峰 | 本地 8 workers 下 JVM 冷路径类加载使各 POST 端点**首次命中** 4s+;单跑/CI 不触发。expect 已调 10s(41cfd10) |

## 硬规则(防复发,已同步 AGENTS.md)

1. **R1 环境两分**:api.http 与 e2e 等自动化**只在 test(8082)** 跑;dev(8081/3001)只做手工 UI 测试,含准真实数据,**禁自动清、禁自动化指 dev**。(用户 2026-11-08 拍板)
2. **R2 api.http 节自含**:新增 spec 节若依赖变量,要么节内自建全部前置(变量后缀隔离,如 `160`),要么在文件头写明「必须整文件按序跑」。禁止横跨多节隐式取变量。
3. **R3 新节先复刻再交付**:api.http 新增/改动的节,交付用户前必须用脚本(curl/python)在目标环境逐请求复刻一遍全绿;「看起来对」不算验过。
4. **R4 归因先问现场**:用户报错先确认「跑的是哪个入口、哪个环境、有无新产物」,再开查;禁止拿上一个案子的结论套新报错。
5. **R5 漂移判定加严**:e2e 红例「单跑绿」只能记疑似漂移;**同晚第二次复现即升级为真 bug**,必须 trace/DB 实锤归因后才许结案。
6. **R6 DB 还原现场**:查「某轮执行留下了什么」(项目/组/类型行)比读日志更硬;静态请求没产生实体 = 请求没发出,先查执行覆盖,再查服务端。
