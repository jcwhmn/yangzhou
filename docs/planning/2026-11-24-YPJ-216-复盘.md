## 元因分析(按因果强度排序)

1. **需求记录失真是第一因。** spec-first 没有防住 spec 自己错:我在 SRS review 轮把用户的原话**转述演绎**(「弹窗列出」→「对话框内行内输入」),交互位置这个需求级语义被悄悄改掉,后续忠实实现 = 忠实返工。教训:用户澄清里的**何时弹/在哪输入/列出什么/提交后发生什么**四要素必须逐句贴原话,转述即风险。
2. **设计文档深度不足(用户点名)。** design 只写了 API 入口落点,后端没写守卫算法(决策序、三调用点收敛、事务边界、幂等分支),前端没列**分支真值表**。实际交互分支:3 途径 × 必填开关 × 有无预估 × 已上板/新拉 ≈ 12+,零枚举——每轮返工都在临场补一个「设计时本该写下的分支」。对比:甘特 SRS v4 有渲染真值表,实现一次过;本票没有,返工六轮。
3. **「恢复」不查原版、重写代替外科手术。** 三轮丢行为(预选中/禁用/文案)全部来自整文件 write 重写;commit 声称「完全恢复原版」却没跑一次 git show 对照 diff。且没先确认用户要的终态是「原版」还是「原版形态+新语义」——把恢复当默认答案,方向本身错了半轮。
4. **没有钉板 e2e,拿用户当测试机。** 四途径交互流到手验收全绿前 e2e 覆盖为零,6 轮往返全靠用户手工发现;0763205 补 5 用例后,后续问题(预填、create 守卫)转为分钟级 e2e 反馈。返工第 2 轮就该先钉板。
5. **e2e 设计不看自己写的约束。** 必填项目建无预估票被自己实现的 create 409 打回——写用例前没过 SRS §四守卫表;平台控件断言(toHaveValue vs 文本可见性)没查既有 spec 惯例。

## 防复发硬规则(建议同步 development.md,待用户拍板)

- **R1 交互措辞贴原话**:SRS 记录用户澄清时,「何时弹/在哪输入/列出什么/提交后发生什么」逐句贴原话,不得合并转述;转述处必须标注请用户复核。
- **R2 恢复=对照恢复**:凡「恢复原版/恢复某行为」必须 `git show <commit>:<file>` 打开原版对照 diff 修改,禁止凭记忆重写;commit 声称「恢复」前先对照自查四项清单(候选集/预选/禁用/文案)。
- **R3 返工第 2 轮先钉板**:同一交互流第 2 次返工,先补 e2e 钉住已对行为再动码;「用户手工验对」不进 e2e 视为未钉住。
- **R4 design 分支真值表**:交互类设计必须列全分支(途径×开关×票状态×新旧成员),每分支写「用户看到什么/点什么/发什么请求」;后端写算法决策序+调用点收敛+事务边界。深度不足不开工(2026-11-24 用户拍板)。
- **R5 终态先行**:返工前先向用户确认终态形态(原版 or 原版+新语义),「恢复」不是默认答案。
