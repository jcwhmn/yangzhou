## 元因分析(按因果强度排序)

1. **验证断言错了对象(技术根因)**。自验闭环 = 操作 → 可见结果 → 刷新持久;我的自验只做到「网络请求 200/204」。
   PUT 204 + 界面不变 = 渲染 bug,这个不对称信号从第一次自验就在手,但我的断言根本看不见界面。
   「验收 = 用户主路径测试绿」七规第一条,写进 development.md 的规则没有变成断言习惯。
2. **症状→动作映射错误(行为根因)**。「点击无反应」的正确第一步 = 从 onClick 起逐行读完调用链(handler→逻辑→渲染),
   纯代码阅读、零环境依赖。我却映射成「环境问题」——因为「我本地是好的」这个假前提(由元因 1 的假绿造成)。
   错误前提 → 错误映射 → 五轮动作全部在环境里打转,且每轮都侵入用户领地(docker/端口/工具链属于用户)。
3. **证据收集不对称**。查后端很勤(直调 API、查库),读前端渲染代码很懒——整个 debug 期间从未完整读过
   `byStatusName` → 渲染那 5 行,根因恰恰就在那 5 行。
4. **用户纠偏信息被惯性覆盖**。「dev 是 docker」「e2e 一直有 playwright」「你不要多做」——用户说过的每一句都是
   第一优先级事实源,我却每次重新解释、继续原路线。信息在,行为没跟上。

## 防再发规则(全部可检查,进 troubleshooting.md 实操教训)

- **R1**「点击/操作无反应」类症状:第一步必须从事件 handler 起逐行读完整个调用链到渲染;禁止在此之前查环境、装工具、起服务。环境假说排在代码路径之后,且必须先给反证。
- **R2** 前端自验必须断言「用户可见结果」(界面文本/DOM 顺序/可见性),不是「网络请求 200/204」。闭环 = 操作→可见变化→刷新→持久。
- **R3** 「后端对 + 界面错」= 渲染路径 bug,直接读渲染代码;「后端错 + 界面对」= 后端 bug。不对称信号本身即定位,不再查 bundle/容器。
- **R4** 环境领地:不装新工具链(先查 node_modules/scripts 既有能力)、不自起服务/杀端口、不动 docker;确需环境给用户命令,由用户执行。
- **R5** commit 前逐文件过目 `git status`;探针产物(token/截图/临时脚本)当轮清理;禁 `add -A` 盲扫。
- **R6** 用户纠偏指令(「你别做了」「回退」「只做 X」)= 立即执行,不复述理由、不扩大动作。

## 对照:这次 e2e 怎么写的(规则落地示范)

board-order.spec.ts 的断言对象是 `visibleOrder` = 页面卡片的**渲染顺序**(乙甲丙),不是 waitForResponse;
waitForResponse 只作时序同步(PUT 落库后再断言),不作为结果断言。这直接把 R2 编进了测试。
