# 动态查询引擎设计方案

## 1. 背景

当前 Sprint / Item 列表查询使用 Spring Data JDBC `@Query` 编写静态 SQL。

随着业务需求增加，Item 列表中的字段逐渐支持：

- 动态搜索
- 动态排序
- 多字段组合排序
- 多表字段搜索
- 多表字段排序
- 特殊计算字段搜索
- 特殊计算字段排序
- 字段配置化、可增减

当前 SQL 通过大量 `CASE WHEN` 实现动态排序，例如：

```sql
CASE WHEN :k1 = 'number' AND :d1 = 'asc'
     THEN i.number
END ASC NULLS LAST,

CASE WHEN :k1 = 'number' AND :d1 = 'desc'
     THEN i.number
END DESC NULLS LAST,

CASE WHEN :k1 = 'title' AND :d1 = 'asc'
     THEN i.title
END ASC NULLS LAST,

CASE WHEN :k1 = 'title' AND :d1 = 'desc'
     THEN i.title
END DESC NULLS LAST
```

当排序字段增加到十几个，并支持 3 个排序优先级时，SQL 已经产生大量重复代码。

如果进一步支持动态搜索条件，则会继续产生大量类似：

```sql
CASE WHEN ...
```

或者：

```sql
(:field IS NULL OR ...)
```

最终导致 SQL 难以维护、测试和扩展。

因此需要将动态查询逻辑从静态 `@Query` 中抽离，建立独立的 Dynamic Query Builder。

---

# 2. 目标

本方案目标：

1. 支持动态 Filter。
2. 支持动态 Sort。
3. 支持多字段组合 Filter。
4. 支持多字段组合 Sort。
5. 支持来自不同表的字段。
6. 支持计算字段，例如 `overdue`、`blocked`。
7. 根据实际使用的字段自动决定所需 JOIN。
8. 对字段、操作符和排序方向进行白名单控制。
9. 保证 SQL 参数全部使用 Prepared Statement / Named Parameters。
10. 保持现有 Spring Data JDBC 用于普通 CRUD。
11. 将复杂查询独立为 Custom Repository。
12. 后续可以扩展新的字段，而不需要大规模修改 SQL。

---

# 3. 非目标

本方案暂时不考虑：

- 任意 SQL 直接暴露给前端。
- 用户自定义 SQL。
- 任意 JOIN。
- 任意数据库函数。
- 通用 BI / Reporting 查询系统。
- 任意表的动态查询。

Dynamic Query Builder 只允许访问系统预定义的字段和关系。

# 5. Repository 分层策略

不建议完全放弃 Spring Data JDBC。

Spring Data JDBC 继续负责普通 CRUD：

```kotlin
interface ItemRepository : CrudRepository<Item, UUID>
```

复杂查询单独增加：

```kotlin
interface ItemQueryRepository {
    fun findPage(query: ItemQuery): Page<Item>
}
```

实现：

```kotlin
class ItemQueryRepositoryImpl(
    private val jdbcTemplate: NamedParameterJdbcTemplate,
) : ItemQueryRepository {

    override fun findPage(query: ItemQuery): Page<Item> {
        // Dynamic Query Builder
    }
}
```

最终结构：

```text
ItemRepository
├── save()
├── findById()
├── delete()
└── ...

ItemQueryRepository
└── findPage()
```

这样可以避免为了一个复杂查询而让整个 Repository 变得复杂。

# 10. Field Registry

Field Registry 是整个 Dynamic Query Builder 的核心。

它负责定义：

- 前端字段名称
- SQL expression
- 字段类型
- 支持的 operator
- 是否支持排序
- 所依赖的 JOIN
- 是否为计算字段

---

# 11. ItemField

第一阶段可以使用 Kotlin enum：

```kotlin
enum class ItemField {
    NUMBER,
    TITLE,
    TYPE,
    STATUS,
    ASSIGNEE,
    PRIORITY,
    START_DATE,
    DUE_DATE,
    FEAS_SIGNAL,
    SPRINT,
    CREATED_AT,
    OVERDUE,
    BLOCKED,
}
```

注意：

API 层不要直接接收数据库字段：

```text
i.number
s.name
m.display_name
```

而应该接收业务字段：

```text
number
status
assignee
```

# 12. FieldDefinition

```kotlin
data class FieldDefinition(
    val field: ItemField,
    val expression: String,
    val type: FieldType,
    val joins: Set<Join>,
    val sortable: Boolean,
    val operators: Set<Operator>,
)
```

例如：

```kotlin
val STATUS = FieldDefinition(
    field = ItemField.STATUS,
    expression = "s.name",
    type = FieldType.STRING,
    joins = setOf(Join.STATUS),
    sortable = true,
    operators = setOf(
        Operator.EQ,
        Operator.NE,
        Operator.IN,
        Operator.NOT_IN,
        Operator.LIKE,
    ),
)
```

# 13. FieldType

```kotlin
enum class FieldType {
    STRING,
    INT,
    LONG,
    BOOLEAN,
    DATE,
    DATETIME,
    UUID,
}
```

FieldType 用于：

1. 参数转换。
2. Operator 校验。
3. 防止错误的查询组合。

例如：

```text
DATE + LIKE
```

应该在 Query Builder 阶段直接拒绝。

# 14. 多表字段

例如：

```text
Item
 ├── status      -> status table
 ├── assignee    -> member table
 └── sprint      -> sprint table
```

FieldDefinition 声明依赖：

```kotlin
STATUS(
    expression = "s.name",
    joins = setOf(Join.STATUS),
)

ASSIGNEE(
    expression = "m.display_name",
    joins = setOf(Join.ASSIGNEE),
)

SPRINT(
    expression = "sp.name",
    joins = setOf(Join.SPRINT),
)
```

Query Builder 根据实际使用的字段计算 JOIN。

例如查询：

```text
status = "Open"
priority > 2
```

只需要：

```sql
JOIN status s ...
```

而不需要：

```sql
JOIN member m ...
JOIN sprint sp ...
```

---

# 15. Join Registry

```kotlin
enum class Join {
    STATUS,
    ASSIGNEE,
    SPRINT,
}
```

对应：

```kotlin
val JOIN_SQL = mapOf(
    Join.STATUS to """
        JOIN status s
          ON s.object_id = i.status_object_id
    """.trimIndent(),

    Join.ASSIGNEE to """
        LEFT JOIN member m
          ON m.object_id = i.assignee_object_id
    """.trimIndent(),

    Join.SPRINT to """
        LEFT JOIN sprint sp
          ON sp.object_id = i.sprint_object_id
    """.trimIndent(),
)
```

具体 JOIN SQL 根据实际数据库结构调整。

# 16. 计算字段

部分字段不是数据库中的直接 column。

例如：

```text
overdue
blocked
```

## overdue

逻辑：

```sql
i.due_date IS NOT NULL
AND i.due_date < :today
AND s.is_final = FALSE
```

可以定义：

```kotlin
FieldDefinition(
    field = ItemField.OVERDUE,
    expression = """
        (
            i.due_date IS NOT NULL
            AND i.due_date < :today
            AND s.is_final = FALSE
        )
    """.trimIndent(),
    type = FieldType.BOOLEAN,
    joins = setOf(Join.STATUS),
    sortable = true,
    operators = setOf(
        Operator.EQ,
    ),
)
```

---

# 17. blocked

```kotlin
FieldDefinition(
    field = ItemField.BLOCKED,
    expression = "(i.object_id IN (:blockedIds))",
    type = FieldType.BOOLEAN,
    joins = emptySet(),
    sortable = true,
    operators = setOf(
        Operator.EQ,
    ),
)
```

注意：

`blockedIds` 应该作为 Named Parameter 传入，而不是直接拼接到 SQL。

# 18. WHERE Builder

例如：

```kotlin
Filter(
    field = ItemField.PRIORITY,
    operator = Operator.GTE,
    value = 3,
)
```

生成：

```sql
i.priority >= :p0
```

参数：

```text
p0 = 3
```

多个条件：

```kotlin
listOf(
    Filter(ItemField.STATUS, Operator.IN, listOf("Open", "Doing")),
    Filter(ItemField.PRIORITY, Operator.GTE, 3),
)
```

生成：

```sql
WHERE
    s.name IN (:p0)
    AND i.priority >= :p1
```

参数：

```text
p0 = ["Open", "Doing"]
p1 = 3
```

---

# 19. Parameter Builder

建议所有动态 value 都通过参数绑定。

不要生成：

```sql
WHERE i.title = 'xxx'
```

而生成：

```sql
WHERE i.title = :p0
```

参数：

```kotlin
params["p0"] = value
```

这样可以避免 SQL Injection，同时让数据库更容易处理参数。

---

# 20. ORDER BY Builder

排序字段只允许来自 Field Registry。

例如：

```kotlin
SortSpec(
    field = ItemField.PRIORITY,
    direction = SortDirection.DESC,
)
```

生成：

```sql
i.priority DESC NULLS LAST
```

注意：

`direction` 不能作为普通 SQL 参数：

```sql
ORDER BY i.priority :direction
```

这是不合法的。

因此 direction 必须通过 enum 白名单转换：

```kotlin
when (direction) {
    ASC -> "ASC"
    DESC -> "DESC"
}
```

# 21. 完整 SQL 生成

最终 SQL 可以类似：

```sql
SELECT
    i.*
FROM item i

JOIN status s
    ON s.object_id = i.status_object_id

LEFT JOIN member m
    ON m.object_id = i.assignee_object_id

WHERE
    i.project_object_id = :projectObjectId
    AND s.name IN (:p0)
    AND i.priority >= :p1
    AND (
        i.due_date IS NOT NULL
        AND i.due_date < :today
        AND s.is_final = FALSE
    )

ORDER BY
    i.priority DESC NULLS LAST,
    m.display_name ASC NULLS LAST,
    i.created_at DESC NULLS LAST

LIMIT :limit
OFFSET :offset
```

# 22. Query Builder

建议拆成多个职责，而不是一个巨大的 Builder。

```text
ItemQueryBuilder
├── FilterBuilder
├── JoinResolver
├── SortBuilder
└── ParameterBuilder
```

例如：

```kotlin
class ItemQueryBuilder(
    private val fieldRegistry: FieldRegistry,
) {

    fun build(query: ItemQuery): BuiltQuery {
        val joins = resolveJoins(query)

        val filters = buildFilters(
            query.filters,
        )

        val orderBy = buildOrderBy(
            query.sorts,
        )

        return BuiltQuery(
            sql = ...,
            parameters = ...,
        )
    }
}
```

```kotlin
data class BuiltQuery(
```

```kotlin
val query = queryBuilder.build(itemQuery)
```

# 24. 分页

分页仍然使用：

```sql
LIMIT :limit
OFFSET :offset
```

但是必须限制最大 page size。

例如：

```kotlin
val limit = request.limit.coerceIn(1, 100)
```

防止：

```text
limit = 100000000
```

造成数据库压力。

# 25. Count Query

如果 API 返回 Page，需要额外生成：

```sql
SELECT COUNT(*)
FROM ...
WHERE ...
```

建议复用相同的：

```text
Filter
+
Join
```

但不要生成：

```text
ORDER BY
LIMIT
OFFSET
```

即：

```text
Main Query
    ├── FROM
    ├── JOIN
    ├── WHERE
    ├── ORDER BY
    ├── LIMIT
    └── OFFSET

Count Query
    ├── FROM
    ├── JOIN
    └── WHERE
```

# 26. 安全设计

Dynamic Query Builder 最重要的原则：

> 用户可以控制查询参数，但不能控制 SQL 结构。

允许：

```json
{
  "field": "priority",
  "operator": "gte",
  "value": 3
}
```

不允许：

```json
{
  "field": "i.priority; DROP TABLE item",
  "operator": "..."
}
```

因此：

## Field 必须白名单

```text
priority -> i.priority
status   -> s.name
```

## Operator 必须白名单

```text
gte -> >=
eq  -> =
in  -> IN
```

## Direction 必须白名单

```text
asc  -> ASC
desc -> DESC
```

## Value 必须 Parameter Binding

禁止：

```kotlin
"$value"
```

直接进入 SQL。

# 28. 为什么不继续使用 `@Query`

`@Query` 非常适合：

```text
固定 SQL
+
少量可选参数
```

例如：

```kotlin
@Query("""
    SELECT *
    FROM item
    WHERE project_object_id = :projectObjectId
""")
fun findByProject(
    projectObjectId: UUID,
): List<Item>
```

但是当前场景属于：

```text
动态 WHERE
+
动态 JOIN
+
动态 ORDER BY
+
动态 operator
+
计算字段
+
多表字段
```

继续使用 `@Query` 会导致：

```text
SQL CASE WHEN 爆炸
        ↓
SQL 可读性下降
        ↓
修改成本增加
        ↓
测试困难
        ↓
新增字段容易遗漏
```

因此复杂查询应该迁移到 Custom Repository。

---

# 29. 为什么不直接让前端传 SQL

虽然这样实现起来最简单：

```json
{
  "where": "i.priority > 3",
  "orderBy": "i.created_at DESC"
}
```

但这是不可接受的设计。

原因包括：

- SQL Injection
- 数据越权
- 隐藏字段泄露
- 表结构泄露
- 查询资源滥用
- 数据库性能风险

因此必须使用：

```text
API Field
    ↓
Field Registry
    ↓
SQL Expression
```

而不是：

```text
API Field
    ↓
SQL
```

---

# 30. 是否需要 jOOQ

如果当前查询复杂度主要是：

```text
动态 WHERE
动态 ORDER BY
少量 JOIN
分页
```

可以先使用：

```text
NamedParameterJdbcTemplate
+
自定义 Query Builder
```

优点：

- 改造成本低
- 不需要引入新框架
- 对现有 Spring Data JDBC 兼容
- SQL 控制能力强

---

如果未来出现：

```text
复杂 AND / OR
嵌套条件
大量 JOIN
子查询
GROUP BY
HAVING
窗口函数
动态 SELECT
复杂聚合
```

建议评估 jOOQ。

jOOQ 更适合构建复杂 SQL DSL。

# 33. 第三阶段

```text
AND / OR
嵌套条件

```

```text
Condition
├── SimpleCondition
├── AndCondition
├── OrCondition
```


```kotlin

    Or(
        Eq(STATUS, "Open"),
        Eq(STATUS, "Doing"),

    Gte(PRIORITY, 3),
)
```

这样可以进一步形成完整的 Filter DSL。

# 35. 性能考虑

动态查询虽然提高了灵活性，但必须关注数据库性能。

## 索引

常用过滤字段需要索引，例如：

```text
project_object_id
status_object_id
assignee_object_id
priority
due_date
created_at
```

多表字段需要根据实际查询模式建立索引。

---

## 避免无意义 JOIN

通过 Join Resolver，只加入真正需要的 JOIN。

---

## 避免无限 OR

如果未来支持：

```text
OR
```

需要限制条件数量和嵌套深度。

---

## 限制分页

例如：

```text
maxLimit = 100
```

```text
              ┌──────────────────────────────┐
              │ ItemQueryRepository          │
              │                              │
              │ NamedParameterJdbcTemplate   │
              └──────────────┬───────────────┘
                             │
                             ▼
                       PostgreSQL


Spring Data JDBC Repository
        │
        ├── CRUD
        ├── save
        ├── findById
        └── simple queries
```

---

# 37. 结论

当前查询已经超出了 Spring Data JDBC `@Query` 最适合处理的范围。

核心问题不是 `ORDER BY` 本身，而是：

> **查询结构正在变成动态的。**

包括：

```text
WHERE
JOIN
ORDER BY
Operator
多表字段
计算字段
Pagination
```

因此不应该继续通过增加：

```sql
CASE WHEN ...
```

来解决。

推荐将查询拆分为：

```text
Query Model
      ↓
Field Registry
      ↓
Filter Builder
      ↓
Join Resolver
      ↓
Sort Builder
      ↓
SQL + Parameters
      ↓
NamedParameterJdbcTemplate
```

同时保留 Spring Data JDBC 处理普通 CRUD。

这种设计可以使新增一个字段从：

```text
修改大量 SQL CASE WHEN
+
修改参数
+
修改 Repository
+
修改排序逻辑
```

降低为：

```text
增加一个 FieldDefinition
```

如果未来查询复杂度继续增长，再考虑将底层实现从：

```text
NamedParameterJdbcTemplate
```

升级为：

```text
jOOQ
```

而上层的：

```text
Filter
Sort
Field Registry
Query Model
```

可以保持不变。
