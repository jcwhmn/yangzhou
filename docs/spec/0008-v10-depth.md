# Spec — yangzhou V10:深度打磨(层次结构 / detail 重构 / 视图与颜色)

> 来源:V10 grilling(2026-09-19,Round 1 全票 + 用户需求清单 docs/requirement/requirement.md 2026-09-19 节);决策记录见 Obsidian CONTEXT.md「V10 已定」与「Defer 总账」。词汇表/ADR 同 V1–V9。

## Problem Statement

V6–V9 解决了自动化与追踪,但产品深度不足:能力词表是平铺的(几十个技能一锅粥)、item 详情所有信息堆在一页、项目列表无筛选排序、看板无颜色语义、收藏不可发现、工时页粗糙。同时用户即将丢掉 Linear 拐棍,yangzhou 要成为唯一管理工具,这些深度缺陷会被放大。

## Solution(七块)

1. **Feasibility 层次结构**:attribute 两层固定(分类 → 技能/标签);词表管理按分类分组;members 页多层表头表格(checkbox 有无 + spinbox 等级)。
2. **Item detail 重构**:常驻 = 标题/状态/assignee/日期;Tab 属性页 = ①详情 ②需求 ③依赖+检查清单 ④工时 ⑤GitHub;评论独立 tab;右 sidebar = 创建/更新/类型/**优先级(新字段 P0–P3 可空)**/feasibility 信号/超期/收藏。
3. **项目列表**:筛选(文本)/排序(名称/信号)/完成状态优先 + 「显示已归档」checkbox 切换。
4. **表格视图**:项目 item 列表表格,列可 toggle 显示/隐藏(持久到 localStorage)。
5. **颜色语义**:member 自动分配颜色(调色板轮转,`member.color` 列);未分配 item 灰色;快超期(due-3天内)橙、超期红(已有)。
6. **GitHub gap**:PR author(`github_username`)→ 自动 assign(池内才指派);真实链路验证一轮。
7. **体验**:收藏 ☆ 常显 + 首次引导;工时页打磨 + 回看板 link;成员移除约束(assignee 且非终态 → 409)。

## Implementation Decisions

- **V23 migration**:`attribute_definition.parent_id bigint null`(FK 自引用;null = 未分类叶子或分类根)+ kind CHECK 扩 `'category'`;`member.color varchar(7)`;`item.priority varchar(2)`(CHECK P0–P3 或空)
- **层次规则**:两层固定——`kind='category'` 行为分类根(parent_id 恒 null);skill/label 可挂 parent_id(分类);parent_id 空 = 「未分类」组(读时分组,不迁存量数据)。能力(capability)仍只挂叶子。分类删除:有子项 409。
- **重算联动**:分类调整不影响 signal(signal 按叶子算)——无重算需求。
- **members 表格**:分类 colspan 多层表头;行 = 成员,列 = 叶子技能;checkbox = 有无(presence),spinbox = 1–4 等级;横向滚动 + 分类锚点。数据沿旧 API(逐成员 caps)。
- **detail 重构**:单页改 tab 布局;URL 不变;渐进加载保留。评论 tab 化(独立滚动)。sidebar 数据全部现成,仅 priority 新增。
- **优先级**:默认空;看板卡片 P0/P1 显示红/橙边;可按 priority 排序(表格视图)。
- **GitHub author 回填**:sync 发现 PR author 时,按 `github_username` 找成员 → **池内**自动 assign(未配置池则跳过自动指派仅留痕)。
- **颜色**:调色板 8 色轮转,member 创建时自动分配;看板卡片左边缘色条 = assignee 颜色;未分配 = 灰色条。

## Testing Decisions
