# 0041 — V20 / YPJ-54:Sprint 成员变更留痕与 scope/reopen 指标

> 需求源:YPJ-54(spec 0037 §五.3);0037 §四「Y54 留痕方向」为本票既有约束。分支 `task/YPJ-54`。
> 流程备注:spec 0041 归本票;YPJ-57 开工顺延 0042。

## 一、需求

### 背景
`item_group_member` 只有 `created_at`、离组即删行:sprint 成员加/离无留痕,scope-change 指标做不出,burnup scope 线(M9)只能按「加入累计」近似(离组后虚高)。

### 范围
1. **留痕**:新表 `item_group_member_history`(episode 式);`item_group_member` 的全部服务层写入路径(加/离)同步留痕。
2. **M11 Scope Change 端点**:`GET /api/projects/{key}/metrics/scope-change?groupId`——sprint 期间加/离次数与净变(Original → Final)。
3. **M12 Reopen Rate 端点**:`GET /api/projects/{key}/metrics/reopen-rate?from&to`——final → 非 final 迁移史统计(history 已有,无 gap)。
4. **M9 burnup scope 线转精确**:消费留痕重放覆盖当日在册成员。
5. 连带:`entities.puml`、`api.http`、`cleanDatabase` 清单、definitions 口径文案。

### 非目标
- burndown(M8)「成员中途变动不回放」口径不动(票面只列 burnup 转准)。
- velocity(M10)成员计数口径不动。
- 前端图表(YPJ-46 的事);本票只交付端点 + 口径文案。
- 存量 removed 事件回填(物理不可能;只回填 added_at,口径注明)。

### 验收(票面)
- [ ] 加/离组全程留痕可查;既有功能不回归
- [ ] scope-change / reopen 端点 + 集成测试
- [ ] burnup scope 历史线精确;口径说明用户可见

## 二、详细设计

### 1. 迁移 `V32__item_group_member_history.sql`(persistence)

形态裁决:**episode 双列**(added_at/removed_at 同行),否决「add/remove 事件流水」——与 `item_status_history` from/to 同行的仓内惯例一致,scope 重放查询直接(覆盖判断一行可判)。

```sql
-- YPJ-54: item_group_member 加/离留痕(episode 式,spec 0041)
create table item_group_member_history (
    id          bigint generated by default as identity primary key,
    object_id   uuid          not null,
    group_id    bigint        not null,
    item_id     bigint        not null,
    added_at    timestamptz   not null,
    removed_at  timestamptz,
    constraint uk_igmh_object_id unique (object_id),
    constraint fk_igmh_group     foreign key (group_id) references item_group (id),
    constraint fk_igmh_item      foreign key (item_id) references item (id)
);
-- 应用层不变量落库:同组同 item 至多一个在册(sprint/release 均为替换式归属)
create unique index ux_igmh_open on item_group_member_history (group_id, item_id) where removed_at is null;
create index ix_igmh_item on item_group_member_history(item_id);

-- 存量回填:仅 added_at 可回填(= created_at);removed 不可回填,口径注明
insert into item_group_member_history (object_id, group_id, item_id, added_at)
select gen_random_uuid(), group_id, item_id, created_at from item_group_member;
```

### 2. persistence 层
- `entities.kt`:`data class ItemGroupMemberHistory(id, objectId, groupId, itemId, addedAt, removedAt)`(主构造直声明四惯例字段)。
- `repositories.kt`:`ItemGroupMemberHistoryRepository : CrudRepository<ItemGroupMemberHistory, Long>`,派生查询 `findByGroupId(groupId: Long)`、`findFirstByGroupIdAndItemIdAndRemovedAtIsNull(groupId, itemId)`。
- 写入 helper:仓库接口 **default 方法** `recordAdd(groupId, itemId, at)` / `recordRemove(groupId, itemId, at)`;recordRemove 找不到 open 行即 no-op(防存量态/幂等)。否决新开 service 类:三个切片共用两个方法,不值一层;调用方自带 @Transactional,仓库内不再开事务。

### 3. 写入点(api,5 处;全部已有方法内加一行)

| 位置 | 现行为 | 新增 |
|---|---|---|
| `SprintService.assignItem` sprintId=null 分支 | `memberships.delete(current)` | `recordRemove(current.groupId, current.itemId, now)` |
| `SprintService.assignItem` 换 sprint | 删旧 + 插新 | recordRemove(旧组) + recordAdd(新组) |
| `SprintService.assignItem` 直接加入 | 插新 | recordAdd |
| `ItemService.create` YPJ-56 sprintId 块 | `memberships.save(...)` | recordAdd(同事务,负例不落库语义保持:块在校验之后) |
| `ReleaseService.assignItem` 移出/换 release + 加入 | `deleteAll` / `save` | 每行 recordRemove / recordAdd(**release 型也留痕**——同一张成员表,口径「全部写入点」) |

**时间源(遵守 Clock 约定)**:SprintService / ReleaseService / ItemService 现均无 Clock 注入,本票触碰即最小步迁移:三服务构造注入 `java.time.Clock`,写入点用 `clock.instant()`;其余存量 `Instant.now()` 散点不动。连带 ItemServiceUnitTest 等单测构造点补 `Clock.fixed(...)`(照 0038 As-built「复用既有 mock」接线法)。

### 4. M11 Scope Change(`MetricsService` + `MetricsController`)

`GET /api/projects/{key}/metrics/scope-change?groupId`(groupId = group objectId,同 burndown/burnup 惯例):

- 校验:group 存在、属该项目、type='sprint';start/end 缺 → 400「sprint 须有起止日期」(同 burnup 文案)。
- 窗口:`from = startDate.atStartOfDay(UTC)`,`to = endOfDayUtc(endDate)`。
- 覆盖判定:`covering(t) = addedAt <= t && (removedAt == null || removedAt > t)`。
- 口径:original = covering(from) 的 distinct itemId 数;final = covering(to);adds = addedAt∈[from,to] 的 episode 数;removes = removedAt∈[from,to] 的 episode 数;net = final − original。
- 响应线型:`ScopeChangeResponse(definitions, groupId, name, startDate, endDate, original, final, adds, removes, net)`;definitions 中文口径,注明「removed 存量不可回填,上线时点起精确」。

### 5. M12 Reopen Rate

`GET /api/projects/{key}/metrics/reopen-rate?from&to`(窗口同 flowTimes:复用 `window()`,默认 90d、上限 365d):

- 分母 = 窗口内**首次**进 final 的 item 数(复用 `completionTs`,与 throughput M2 同口径)。
- 分子 = 分母中存在 `fromStatusId∈final && toStatusId∉final` 迁移行(createdAt ≥ 该 item 首次 final 时刻)的 distinct item 数。
- rate = reopened/completed;分母 0 → `rate: null`(definitions 注明「无完成则不计率」)。
- 响应线型:`ReopenRateResponse(definitions, from, to, completed, reopened, rate: Double?)`。

### 6. burnup scope 转精确(改 `MetricsService.burnup`)

- `sprintData` 返回值 Triple → 追加 episodes 一项(`ItemGroupMemberHistoryRepository.findByGroupId(g.id)`);velocity 调用点同步改形,取数逻辑不动(M10 口径妥协保留)。
- `scope(d) = episodes.count { covering(endOfDayUtc(d)) }`(**distinct itemId 计数**,换掉 joinTs 计数)。
- `D_BURNUP` 文案改:「scope = 当日在册成员累计(按留痕重放);存量离组不可回填,上线时点起精确」。

## 三、手工测试用例(用户 build/debug 执行)

1. 建 sprint S1,详情页 assign item A → 库查 `item_group_member_history` 出现 1 行 removed_at 为空。
2. A 换指派到 S2 → S1 行 removed_at 非空,S2 新 open 行。
3. A 移出 S2 → S2 行 closed。
4. 创建 item 时直选 sprint(YPJ-56 路径)→ 新 open 行。
5. release 指派/移出 → 同样留痕。
6. `GET scope-change` 核对:造「S1 开始后加 1 人、移出 1 人」数据 → adds=1,removes=1,net=0。
7. 完成一个 item 再拖回非 final → `reopen-rate` reopened=1。
8. burnup 图/端点:含中途移出的 sprint,scope 线在移出日后回落;tooltip 口径文案已更新。
9. 回归:burndown / velocity / flow-times / throughput 各端点照旧。

**偏差(2 处)**:

1. **burnup 内部结构微调**:设计写「sprintData 返回值 Triple 追加 episodes」,实现保持 sprintData 原样未改——burnup 与 scopeChange 各自直查 history(一次 `findByGroupId` 调用,不共享取数),少改一处形参链,velocity 调用点零触碰。
2. **api.http 负例选型**:设计拟负例为「无日期 sprint 的 scope-change 400」,实现改测「组不存在/非本项目 404 与 400 文案」,与 M11 校验序一致;无日期分支由集成测试覆盖,api.http 不重复。

**实现期记坑(2 雷)**:

1. **`-Xjvm-default=all`**(backend/build.gradle.kts):Kotlin 接口 default 方法默认编 `DefaultImpls`,Spring Data 代理调不到 → 留痕 helper 静默不生效,症状表现为移出 PUT 500 / 删组 409(helper 无状态断言被吞)。加编译器开关后愈。诊断范式:测试结果 XML 的 access log 逐请求看 status + `ExchangeResult` 响应体——「数据库约束冲突」≠「sprint 非空」,一字之差换根因。
2. **V32 FK `on delete cascade`**:初版 history FK 未级联,删 sprint 被 history 行挡住(判空只查 `item_group_member`)。改为 `on delete cascade` 后判空语义不回归;item 永软删,cascade 对 item 路径不触发。
