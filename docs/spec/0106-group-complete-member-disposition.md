# 0106 — 组完成时未完成 item 的处置(需求+设计)

> 用户拍板(2026-11-06):① Done(终态)保留在原组,无异议;② 其余 item(一切非终态成员)按「看板新建 item」同一决策树进入其它进行中组,但保留回 Backlog 的可能。

## 一、需求

### 1.1 行为矩阵(用户在组页点「完成组」并确认那一刻)

| 成员状态 | 处置 |
|---|---|
| 终态(Done) | 原样保留在已完成的组里(历史事实),永不移动 |
| 非终态(To Do / 进行中 / 评审 / QA…) | 进入**处置流程**(1.2),用户逐个定去向 |

### 1.2 处置流程(存在非终态成员时)

1. 组状态先迁移为已完成(用户意图明确,先落定)。
2. 随后弹出**处置弹窗**:「完成「组名」——N 个未完成 item 待处置」:
   - **目标组**按看板建 item 同一决策树确定(0105 §1.1 复用):进行中 1 个=直指;多个=选择;0 进行中+计划中≥1=确认激活其一;无非完成态实例=新建并激活(默认名=类型名+序号)。
   - **成员列表**逐行默认「转入目标组」;每行可独立切为「回 Backlog」。
   - 底部「确认处置」逐行落库。
3. **中途关闭弹窗(取消处置)= 合法**:未处置的非终态成员自然落 Backlog(组已完成,Backlog 谓词天然收容)——即「回 Backlog 可能」的兜底形态,不丢数据、无游离(它们不在看板,在 Backlog 页)。

### 1.3 不变式

1. Done 成员永不移动(留在已完成组 = 历史事实)。
2. 处置后不存在「item 归属已完成组且非终态且不在 Backlog 决策内」的悬置态——每个非终态成员要么挂非完成态组、要么入 Backlog。
3. 任何失败/中断,item 的最终状态 ∈ {目标组, Backlog, 原(已完成)组历史行}——三者均合法可见,不丢失。

### 1.4 需求决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | Done 留组 | 用户拍板,无异议;membership=历史事实(裁决 2 现状) |
| D2 | 非终态成员默认进目标组(决策树同 0105),可逐个覆写回 Backlog | 用户拍板「和新创 item 一样逻辑,但保留回 Backlog 可能」 |
| D3 | 先完成组、后处置 | 用户意图先落定;中断/失败天然落 Backlog(合法兜底),无游离、无回滚复杂度 |
| D4 | 逐 item 调用既有归属端点,非原子批量 | 零后端改动;失败项留原组历史行 + 提示名单,不阻塞其余 |
| D5 | 无非终态成员时维持现行确认框 | 零成员=零处置,现状已正确 |
| D6 | 术语「组」 | 0101 案B/0105 D9 |

### 1.5 非目标

- 逐 item 的状态迁移(处置只管归属,不动 item 状态)
- 批量事务端点(逐个调用已满足 N≈一个 sprint 规模;失败可重试)
- 处置弹窗内的 item 详情编辑

## 二、设计

### 2.1 交互流

`sprint 页「✓ 完成组」` → 现行确认框改造:
- 无非终态成员:现状「确认完成」不变(D5)。
- 有非终态成员:确认框升级为**两步**:确认完成 → 处置弹窗(1.2)。
- 目标组确定交互复用 0105 已实现的组件形态(单选直指/列表选/激活确认/新建名称框)。

### 2.2 落库调用(全部既有端点,零后端改动)

- 挂入目标组:`PUT /api/items/{id}/group-membership {groupId: 目标组}`
- 回 Backlog:`PUT /api/items/{id}/group-membership {groupId: null, groupType: <level-1 typeKey>}`
- 逐个顺序调用;单项失败:收集进失败名单(`setError` 汇总「X 个处置失败:item A、item B」),该项留在已完成组历史行,用户可在组详情页或 Backlog 观察后手动处理;其余项继续。
- 激活/新建目标组的链路与失败降级同 0105 §2.1(防重同名复用;激活失败组留计划中、item 照常挂入)。

### 2.3 边界(标注)

- 处置期间用户关闭页面:已处置项保留,未处置项落 Backlog(1.2-3 自洽)。
- 目标组为「新建」且激活失败:同 0105 降级(item 挂计划中组,补集看板可见)。
- 成员含子 item:子 item 独立成员行,独立处置(父item 归属变化不级联,现状语义)。

### 2.4 前端触点

`sprint/[id]/page.tsx`(完成确认框扩展 + 处置弹窗)、`lib/sprints.ts`(如有需要的小 helper)、`lib/texts.ts`(文案,一律「组」)、e2e `group-complete-disposition.spec.ts`。后端零改动。

### 3.1 e2e

1. 完成含三类成员的组 → 处置弹窗列出 2 个非终态(Done 不列)
2. 默认全转入目标组(单进行中直指)→ 确认 → 两 item 挂目标组、Done 留原组、原组不出现于进行中列表
3. 覆写一行「回 Backlog」→ 该 item 在 Backlog、其余在目标组
4. 目标组=多进行中 → 列表选择
5. 目标组=激活计划中 / 新建并激活(确认链)
6. 取消处置 → 非终态成员落 Backlog
7. 无非终态成员 → 现行确认框,无处置步
